# Functional QA ด้วย Haiku Personas

ทดสอบ **business flow จริงจนจบธุรกรรม** ด้วย Haiku หลายตัวขับ Playwright — ต่างจาก `ui-usability-loop` ตรงที่นั่นวัด usability (หาปุ่มเจอไหม เข้าใจง่ายไหม, screenshot-only, ห้ามอ่าน code) แต่อันนี้วัด correctness ของ flow: สร้างเอกสาร, ขออนุมัติ, เปลี่ยนสถานะ, ตรวจผลลัพธ์จริง ถ้าโจทย์คือ "หน้านี้ใช้ง่ายไหม" ให้ไปใช้ `ui-usability-loop` แทน

## ขั้น 1 — จัดกลุ่มตาม business scenario ไม่ใช่แค่จำนวน

แบ่ง personas เป็นกลุ่มตาม flow ธุรกิจเฉพาะ (ที่ใช้จริง: 20 คน → 5 กลุ่ม × 4 คน) เช่น:

- เงินสด/เงินเชื่อ + ขอส่วนลด + อนุมัติ/ปฏิเสธ
- credit holding เกินวงเงิน + อนุมัติ/ปฏิเสธ
- PO approval
- ส่วนลดรายบรรทัด

ต่างจาก ui-usability-loop ที่สุ่ม 10 persona ทำ task เดียวกันหมด — ที่นี่แต่ละกลุ่มมี mission ต่างกัน แล้วใช้ความซ้ำซ้อน**ภายในกลุ่ม** (4 คน/flow) + ความอิสระ**ข้ามกลุ่ม**เป็นตัว cross-check ตอนสังเคราะห์

## ขั้น 2 — เขียน `00-mission-control.md` (shared briefing บังคับอ่านก่อนเริ่ม)

ไฟล์เดียวที่ทุก agent ต้องอ่านก่อนเริ่ม ต้องมีครบ:

1. **Login bootstrap ที่ดึง token จาก e2e fixture เดิมในโปรเจกต์** ด้วย `fs.readFileSync` + regex — **ห้าม copy JWT/token จริงมาวางในไฟล์ briefing ใหม่เด็ดขาด** (token มีอยู่แล้วในไฟล์ที่ commit ไว้ การอ้างอิงไม่สร้าง exposure ใหม่ แต่การ hardcode ซ้ำในไฟล์ใหม่จะโดน auto-mode classifier ของ Claude Code flag เป็น "credential leakage" — เจอจริง เกือบโดนบล็อกทั้ง job)
2. **ตาราง path/URL ที่ verify แล้วจริงจากการ grep route file** — ห้ามเดาจากความจำ (เจอจริง: เดา `om/sale-order` ที่จริงคือ `om/sale-orders` พหูพจน์ ทำให้ 3/5 กลุ่มต้องรันซ้ำ 2-3 รอบ เสีย token มหาศาล)
3. **กติกาเฉพาะโดเมน** เช่น "ถ้าเจอ dialog ขอ OTP ห้ามเทส OTP จริง ให้เลือกช่องทางแนบไฟล์แทนเสมอ"
4. **Known E2E gotcha พร้อม code snippet วิธีแก้** เช่น stuck overlay (ดู skill `playwright-manual-verification` สำหรับ fix 2 ชั้น)
5. **รูปแบบรายงานบังคับ** (ข้อถัดไป)

## ขั้น 3 — รูปแบบรายงานบังคับต่อ persona

- Task ที่ได้รับ
- ผลลัพธ์: สำเร็จ / บางส่วน / ไม่สำเร็จ
- ขั้นตอนที่ทำจริง
- ข้อดี / ข้อเสีย
- **ปัญหาที่เจอ — บังคับอย่างน้อย 1 ข้อเสมอ ห้ามแต่งเดา ต้องมาจากสิ่งที่สังเกตเห็นจริง**
- คะแนน UI-UX 1-10, คะแนนการค้นหาสินค้า 1-10

## Gotchas จากการรันจริง

- **Background agent ที่ notify ว่า "completed" อาจไม่ได้จบจริง** — เจอ agent ตัวหนึ่งรันต่อเบื้องหลังอีกเกือบ 5 ชั่วโมงหลังรายงานผลครั้งแรก (ที่ว่าล้มเหลว) แล้วแก้ปัญหาเองจนสำเร็จ เขียนทับไฟล์ผลลัพธ์ด้วยเวอร์ชันที่ดีกว่ามาก → ถ้า notification แรกรายงานล้มเหลว/บางส่วน **อย่ารีบ retry ทันที** — task-id เดิมอาจ notify ซ้ำอีกทีพร้อมผลที่ดีกว่า
- **ทุก persona ใช้ JWT บัญชีเดียวกัน (single test account) = "ผู้ขอ" กับ "ผู้อนุมัติ" เป็นคนเดียวกันเสมอ** — flow อนุมัติข้ามบทบาทไม่เคยถูกทดสอบจริง ต้องระบุข้อจำกัดนี้ชัดใน**รายงานสังเคราะห์** (ไม่ใช่ฝังไว้แค่รายงานดิบ) และเสนอรอบหน้าใช้บัญชีคู่ requester ≠ approver

## ขั้น 4 — สังเคราะห์ (แนะนำ model แรงสุดที่มี เช่น Opus)

แยกปัญหาทุกข้อเป็น 3 กลุ่มเสมอ:

| กลุ่ม | เกณฑ์ |
|---|---|
| (ก) บั๊กจริงน่าเชื่อถือสูง | หลายกลุ่มอิสระเจอตรงกัน หรือรายละเอียดเชิงเทคนิคชัดตรวจซ้ำได้ |
| (ข) น่าสงสัยต้องตรวจเพิ่ม | อาจเป็นเพราะ shared-test-account หรือ Haiku เขียน selector เองผิด |
| (ค) known test-harness artifact | ไม่ใช่บั๊กแอป |

**ต้อง cross-reference ข้ามกลุ่มก่อนสรุปเสมอ** — เช่น กลุ่มหนึ่งบอกฟีเจอร์หาย แต่อีกกลุ่มใช้ฟีเจอร์เดียวกันสำเร็จวันเดียวกัน = selector ผิดของกลุ่มแรก ไม่ใช่บั๊กจริง

## ขั้น 5 — Phase 0 "verification sprint" ก่อน implement

หลังสังเคราะห์เสร็จ **อย่าเพิ่งแก้** — ไล่ตอบ unknown ที่ severity ของแต่ละ finding ขึ้นกับมันก่อน (เช่น "backend block mutation ไหมระหว่างสถานะนี้" ตอบได้จากอ่านโค้ด 15-30 นาที ไม่ต้องเดา):

- เรียงจาก**ถูกสุด/เร็วสุดก่อน** (อ่านซอร์สโค้ด) → แพงสุด (query permission จริง)
- ผลจริงจาก session ต้นแบบ: ตอบครบ 4 unknown ใน 45 นาที เร็วกว่าประมาณการ 1 วันมาก
